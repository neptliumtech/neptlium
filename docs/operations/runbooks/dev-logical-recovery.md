# Neptlium Dev logical recovery rehearsal

This workflow supports the [Clerk Preview recovery gate](clerk-preview-acceptance.md) on the free Supabase plan. The source is exclusively Neptlium Dev `ntbaoylcrwkowqqvzkno`. Production `udghxwlhztwxvkjaefjh` is outside the rehearsal. The first hosted run is scoped to the pre-rollout, empty application schema. An application relation, routine, type, or migration schema appearing on Dev stops the run and requires a new backup scope review.

## Architecture and cost

[Dev logical recovery rehearsal](../../../.github/workflows/dev-recovery.yml) uses a GitHub-hosted Linux runner and two per-job services based on the same digest-pinned official PostgreSQL 17.11 image. The recovery service has no published port or host bind mounts. Before restore, the script verifies dedicated container IDs and labels and disconnects the recovery service from Docker networks. PostgreSQL tools access the recovery service only through its local Unix socket via Docker. The hosted client service reaches Dev only through the fixed direct host or the Dashboard-verified shared **session** pooler on port 5432. The pooler supplies IPv4 on the free tier.

The design uses no additional Supabase project, upgrade, or paid add-on. Each job is capped at ten Linux runner minutes and uploads no artifacts. The repository is public and standard GitHub-hosted Linux runners are free for public repositories. Confirm the configured runner and repository Actions policy before dispatch. PostgreSQL services and their volumes are disposable. No external backup storage is required for this rehearsal. [Supabase connection modes](https://supabase.com/docs/guides/database/connecting-to-postgres) · [GitHub service containers](https://docs.github.com/en/actions/using-containerized-services/about-service-containers)

## Approval and credentials

Use the existing GitHub Actions access controls and a dedicated `neptlium-dev-recovery` environment. Keep the hosted job restricted to manual dispatch from the default branch. Review the exact trusted workflow revision before adding credentials. Restrict environment deployments to the protected default branch. Require an independent reviewer, prevent self-review, and disable administrator bypass. Keep environment secrets unset until those protections can be verified. PR runs execute only the synthetic job and receive no hosted recovery secrets. The workflow token has `contents: read`. The operator triggering this manual workflow needs repository write access. That permission alone does not release the environment secrets.

| Setting | Required content |
|---|---|
| Environment secret `DEV_RECOVERY_DB_PASSWORD` | Temporary password of a dedicated Dev-only login named `dev_recovery_reader`. Use a separate credential from production, owner logins, and service-role keys. |
| Environment secret `DEV_RECOVERY_CA_PEM` | Trusted CA PEM for the verified Dev direct endpoint or session pooler. Libpq uses hostname verification. |
| Environment variable `DEV_RECOVERY_SOURCE_HOST` | Exact hostname from the Dev Dashboard connection settings. The script fixes the database to `postgres` and port to `5432`, and constructs the session-pooler username with the Dev project ref. |
| Environment variables `DEV_RECOVERY_APPROVAL` and `DEV_RECOVERY_RETENTION` | Approved change or review reference and the literal `ephemeral-job-only`. These record the authorized run and data-handling choice. |
| Environment variable `DEV_RECOVERY_APPROVED_SHA` | Exact reviewed 40-character default-branch commit. A different dispatch revision fails before the source is contacted. |

The Dev owner must separately approve provisioning or reuse of the login. Set its default transaction mode to read-only. Require no role memberships, elevated role attributes, or public-schema CREATE privilege. For this empty, schema-only rehearsal require effective `CONNECT` on database `postgres`, `USAGE` on schema `public`, and standard read access to PostgreSQL catalog metadata. Table or sequence SELECT, schema ownership, role membership, and BYPASSRLS are unnecessary. Check grants through PUBLIC as well as direct grants. The default read-only setting is defense in depth. The grant restrictions and the exported read-only transaction provide the actual boundaries. Do not grant access to Auth password hashes, Storage objects, the managed secrets schema, production resources, or unrelated schemas. Verify the Dev project's managed Auth and Storage counts using separately authorized read-only catalog access before dispatch. If the shared pooler cannot authenticate the custom role with verified TLS, stop and use an approved IPv6-capable runner against the direct endpoint. The workflow never substitutes an owner login. A later populated backup needs a separate review. Reading data would require USAGE on each selected schema, including any migration-history schema, SELECT on each selected table or materialized view, and SELECT on sequences whose state must be restored. The normal complete dump sets row security off and fails when the role is subject to RLS. Enabling row security can produce a partial dump and cannot certify complete recovery.

## Checkpoint, verification, and retention

1. Use a maintenance window for the empty pre-rollout Dev source. Verify the Dev project ref and source inventory, current PostgreSQL major, no application objects or migration ledger, no Auth users, and no Storage buckets or objects. Archive mode is only a database setting. Record the baseline and job revision in the recovery evidence.
2. The workflow checks the source connection uses the restricted read-only role. It checks the empty scope in an exported PostgreSQL repeatable-read, read-only snapshot and uses that same snapshot for the fingerprint and schema-only custom `pg_dump` archive. It streams the archive directly into AES-256 encryption with a fresh random passphrase. The encrypted archive, passphrase, GPG state, and private diagnostics stay in a job-private temporary directory. There is no plaintext dump file. Verify the encrypted file's SHA-256 before decryption. Log the ciphertext checksum and status only.
3. Restore in one transaction through the local socket of the disconnected recovery service. Bootstrap inert PostgreSQL roles for reviewed ACL names. Preserve schema ownership and object ACLs in the dump. Unknown role or extension dependencies must fail the rehearsal. Compare normalized source and restored SQL fingerprints, including data, grants, policies and schema ownership. Compare the source fingerprint again after restore. This checks source consistency within the approved backup scope. The source connection is read-only throughout.
4. One synthetic job verifies an application table, rows, ACLs, an actual row-level policy decision, and a migration-history row. A second job connects as the restricted reader and exercises the same exported snapshot and schema-only flags as the hosted job. The target recreates a NOLOGIN role for the reader to preserve its schema grant without copying credentials. Hosted mode explicitly requires the migration schema to be absent. A successful hosted run will verify the empty application's schema and ACLs only. Managed Auth users, identity settings and signing material, Storage metadata and blobs, managed secrets and encryption keys, extensions outside the scope, and global role passwords and memberships are excluded. Synthetic Auth and Storage rows prove they are excluded from the archive. A later populated schema requires separate backup and restore coverage for those surfaces.
5. The workflow deletes the encrypted archive, passphrase, CA scratch copy, and private logs at job exit. The runner disposes of the service containers and local volumes. Retain only the run URL, commit, checkpoint checksum, timestamps, and pass/fail statements under the approved log retention policy. Revoke or rotate the temporary Dev login credential and remove the environment secret after the rehearsal. This runner-local checkpoint cannot be used for later production or Dev rollback. A durable checkpoint requires a separate approved retention and key-management design.

## Run order

1. Run both synthetic jobs in the draft PR. They must pass rejection of production references, unsafe source hosts, overlapping container IDs, missing credentials, and missing approval or retention. It must also complete the encrypted restore using synthetic data.
2. Review and register the workflow on the default branch through the normal repository process. Independently confirm the environment approvals, exact Dev role, CA and hostname, empty-scope inventory, runner allowance, and the ephemeral retention procedure. Then dispatch **Dev logical recovery rehearsal** with `hosted_dev=true`. Do not enable secrets or run the hosted job before the approval.
3. Compare the read-only Dev inventory before and after, and attach the run evidence. A source mismatch, missing dependency, failed cleanup, or failed restore blocks completion. Dev schema rollout remains a separate approval, even if the rehearsal passes.
